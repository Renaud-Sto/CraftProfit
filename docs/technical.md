# CraftProfit technical documentation

[Back to the README](../README.md) · [User guide](user-guide.md) · [Contributing](../CONTRIBUTING.md)

Target: **World of Warcraft: Forever** beta, build 1.60.1, `## Interface: 16001`. The client uses the Mainline (Midnight-style) UI and API set on a Classic base, Lua 5.1, and the *secret values* restrictions. The addon is about 7,000 lines of Lua (locales and data tables included) and has no library dependency.

## Design principles

1. **Pure logic apart from the game.** Everything that decides a number is plain Lua with no WoW API, tested offline. Game calls live in thin adapters.
2. **An unknown is never a zero.** A missing price is `nil`, shown as `?`. A recipe with any unpriced reagent has no total and no verdict (*Incomplete*), never a cheap-looking one.
3. **Identifiers, not names.** Items, recipes and professions are handled by id. No logic depends on a displayed (localized) text, and tooltips are never parsed.
4. **Defensive at the boundary.** Every game call that may differ between builds is guarded (`pcall`, type checks, `issecretvalue`); a missing API degrades a feature, it never raises a Lua error.
5. **No taint.** The window is parented to `UIParent`, never to a Blizzard frame. The only Blizzard UI touched is the auction house search box and quantity input, defensively, and the addon never presses Buy.
6. **Saved data is repaired in place.** WoW keeps a reference to the table it loaded, so replacing it would silently lose the data at logout.

## Data flow

**Selecting a recipe.** `Trade.watch` polls the profession window every 0.3 s (the Professions UI has no selection event and is created lazily). A new selection id makes `Trade.readSelected()` return a raw recipe, `Recipes.normalize` validates it, and `Controller.setRecipe` renders it. Item data that is not cached yet is requested once (`C_Item.RequestLoadItemDataByID`) and `ITEM_DATA_LOAD_RESULT` triggers a coalesced refresh.

**Rendering.** `Controller.refresh()` calls `Evaluate.run` with the recipe, a price lookup (`Prices.priceOf`), item facts (`Controller.itemInfo`), the commission, the per-point option, the disenchant lookup, whether the character knows Enchanting, and the number of crafts. `Present.build` turns the result into a model (`banner`, `tiles`, `materials`, plus the older `lines`, cost lines, `verdict` and age) and `Window.render` draws it. The window draws the banner (label, best way to sell, net result with its tone), the three tiles and the Materials panel from the new fields, and reads `lines` only for the `likely` (grey disenchant line) and `perpoint` (Cost per skill point value) entries. `lines` and `verdict` are kept in the model for the pinned list and for tests. The pinned list evaluates each pin the same way, always for one craft.

**Searching prices.** `PinsUI.startSearch(recipes)` builds the list of items the recipes need (`PinsUI.wantedFor`, over `Evaluate.wantedItems`: reagents, output, disenchant materials when relevant); a crafted item bound on pickup (`Evaluate.isBindOnPickup(itemInfo(outputItemID))`, the rule `Evaluate` and `Controller.historyItems` use) is left out, since it can never be sold at the AH (its AH tile shows n/a), so it is neither searched nor counted in the summary; an output whose info is not loaded yet is still searched. The list runs through a `PriceQueue`: one `SendSearchQuery` at a time, advanced by `COMMODITY_SEARCH_RESULTS_UPDATED` or `ITEM_SEARCH_RESULTS_UPDATED` or a timeout (6 s; an item the AH keeps refusing is abandoned after 3 timeouts). `recipes` nil means every pinned recipe (**Refresh pinned**); `Controller.refreshRecipe()` passes `{ state.recipe }` (**Refresh recipe**; no recipe: nothing; AH closed: `SEARCH_NEED_AH` in chat). The search runs in two passes: when the first pass ends (not cancelled), the items it missed (did not answer, or answered with no usable listing) are searched once more by a new `PriceQueue` with only those ids, in the first pass's order and with the same timeout, the status showing `SEARCH_RETRYING` ("Retrying %d/%d"); there is no third pass. The summary counts both passes over the first pass's total: `ok = total - still failed`, `noListing` and `failed` from the second pass only, so a price found in pass 2 counts as updated and is not named as missing. One ticker drives whichever queue runs; `PinsUI.state` stays "running" across both passes (the Refresh recipe button stays off); closing the AH cancels the current pass and ends the search. `Controller.commitSearch` (one history batch) and the final refresh run once, when the whole search ends; `recordListings` stores and marks for history only a usable listing, and pass 2 only asks for items pass 1 did not store, so a retry never records an item twice. Measuring why searches miss: `docs/probe-findings.md` F13 (`/cpp trace`). Only one search runs at a time: a start while one runs is ignored, so a recipe refresh never cancels or mixes into a pinned refresh; the no-listing counter is reset at every start. Closing the AH cancels it. `AHAdapter` reads the listings into `{ unit, qty }` rows; `Controller.recordListings` stores the median and answers false for an empty list. At the end, `Controller.commitSearch` records history and the status is `PinsUI.searchSummary(L, { ok, total, noListing, failed })` (pure): `ok` = items whose search returned, with or without listings, `failed` = items that did not answer (`ok + failed = total`), `noListing` = answered with no usable listing. The updated number is the prices actually stored, `ok - noListing`, so updated + no listing + no answer = total. The unit is a price, one per item searched (reagents, crafted item, disenchant materials), so a recipe with 5 reagents can count 7. All stored: `SEARCH_UPDATED` ("Updated %d prices"); otherwise `SEARCH_UPDATED_OF` ("Updated %d of %d prices", possibly "Updated 0 of 12 prices") followed by `SEARCH_NO_LISTING` (" · no listing: %s (nobody is selling them now)") and/or `SEARCH_NO_ANSWER` (" · no answer: %s, try again"). `%s` is the item names, read at summary time through `Controller.itemName` ("#id" when not loaded), when there are at most two of that kind (`noListingIDs` collected in `onItem`, `failedIDs` from the queue summary), else the count; it comes after a colon so one wording reads right for 1 and many (French puts a non-breaking space before the colon). The status font string is a fixed box (`STATUS_H` 28 px, two lines, word wrap, `SetMaxLines(2)` guarded): a longer text is cut with "...", never drawn past the window. A cancelled search says `SEARCH_CANCELLED`; a list with no item to price starts nothing and says `SEARCH_NOTHING` ("Nothing to search"). The three levels: Refresh recipe (a few seconds), Refresh pinned (about a minute for 20 recipes, measured 2026-10-11 on the beta), Scan AH (one full scan, 15 minute server cooldown).

**The Refresh recipe button.** `Window.parts.refresh`, a `Native.button` on the third option row right of Pin/Unpin; both are `(body width - 16 - 6) / 2` = 161 px, 6 px apart (the row count and the window height are unchanged). `Window.updateRefreshButton()` enables it only when `ns.AH.isOpen`, a recipe is rendered (`Window.lastModel`, cleared by `showEmpty`) and `PinsUI.state ~= "running"`; it sets `b.enabled` and `SetEnabled` (guarded), and the click handler checks `enabled` too. It runs on every render and `showEmpty`, at the end of `Controller.onAHOpen` (both ways: the hidden window keeps its last model), and when a search starts and ends.

**Scanning.** `AH.requestSnapshot` calls `ReplicateItems` (once per 15 minutes per account). The client then fires `REPLICATE_ITEM_LIST_UPDATE` hundreds of times for one scan, so the adapter schedules **one** read one second after the first event and ignores the rest until 10 seconds after that read. The read walks the rows in chunks of 1,500 per frame (no freeze) into a `Prices.newAggregator()`; `Controller.onSnapshot` merges the result into the saved prices. A scan started by another addon is handled the same way. Each chunk is read under `pcall`: a read that raises ends that scan and frees the reader, so a later scan in the same AH session is read again.

**Clicking a reagent.** `AH.browse` switches the auction house to its Buy view, writes the name in `SearchBar.SearchBox` and calls `SearchBar:StartSearch()`. A hook on `CommoditiesBuyFrame`'s `OnShow` then sets the quantity input (`SetQuantity`) and calls the input's own `OnTextChanged` handler with `userInput = true`, which makes the client recompute the quote, as typing would. The preset expires after 60 s and is dropped when the AH closes.

**Clicking the crafted item.** `Controller.onOutputClick` (wired to the AH tile and the window title) does nothing without a recipe; with the AH closed it says `SEARCH_NEED_AH`; an output bound when picked up (`Evaluate.isBindOnPickup`) says `SEARCH_UNSELLABLE` and searches nothing; an item whose name is not loaded says `ITEM_NOT_LOADED`; otherwise it calls `AH.browse(name, itemID, nil)`, the same path as a reagent click with no quantity preset, so the quantity hook is not armed.

**The search icon.** `Native.searchIcon(texture)` puts the game's magnifier on a texture and returns whether it did: first the atlas `Native.SEARCH_ATLAS` (`common-search-magnifyingglass`) when `C_Texture.GetAtlasInfo` knows it, else the icon of the AH search box (`AuctionHouseFrame.SearchBar.SearchBox.searchIcon` or `SearchIcon`, by `GetAtlas`, else `GetTexture` with `GetTexCoord`). It never guesses a file path (a missing file draws a green square) and draws nothing when no source exists, so the icon is optional; everything runs in `pcall`. `Native.forwardDrag(button, window)` lets a button that covers a drag handle start and stop the window move. `Window` shows the title and AH tile icons only while the AH is open and a recipe is displayed.

**Screen fit.** `Native.fitToScreen(window)` reads `UIParent:GetHeight()` and the window's height. When the window is taller than the screen less `Native.FIT_MARGIN` (20 px), it calls `SetScale(room / height)`, else `SetScale(1)`. A height that is not a finite positive number, or a call that raises, changes nothing. The options and History windows call it on open.

**Native templates.** `UI/Native.lua` draws with the game's own templates instead of hand-painted textures: `Native.window` is a `ButtonFrameTemplate` with `ButtonFrameTemplate_HideAttic`, `_HidePortrait` and `_HideButtonBar` applied in that order (HideAttic resets the inset's left edge, HidePortrait then moves it), so its content area, `frame.Inset`, runs from TOPLEFT (9, -24) to BOTTOMRIGHT (-6, 4); the title bar is 20 px, the close button 24 px at TOPRIGHT (-2, 1). Buttons are `UIPanelButtonTemplate` (22 px, label cut instead of wrapping), check boxes `UICheckButtonTemplate` (24 px, the label widens the hit area), inputs `InputBoxTemplate` (22 px, its border reaches 5 px left of the box), panels and tiles sit on `InsetFrameTemplate` with header strips and cards from atlases (`Native.HEADER_VARIANTS`, `Native.TILE_VARIANTS`); fonts are game font objects only. Rules the module keeps: every template internal (`Inset`, `TitleContainer`, `CloseButton`, `Text`, the `ButtonFrameTemplate_*` helpers, colour objects, `C_Texture.GetAtlasInfo`) is tested with `type(...)` before use and has a plain fallback, so a changed client build never raises; a templated frame that could sit under a Blizzard panel is created with a nil parent and then `SetParent`, because the gamepad navigation hooks `CreateFrame` and runs tainted under an open Blizzard panel (the exception is a frame made directly from `NineSlicePanelTemplate`: it reads its parent's `layoutType` in `OnLoad` and errors without a parent; a template that holds a `NineSlice` child, such as `ButtonFrameTemplate` or `InsetFrameTemplate`, is fine either way. Panels and tiles create their inset with their own frame as parent, which is never a Blizzard panel); no dropdown or `Menu` API (crashes the Forever client), no `StaticPopup_Show`, no `UIPanelWindows` (Escape goes through `UISpecialFrames`), no hook on Blizzard methods and no write into Blizzard tables other than adding a name to `UISpecialFrames`; anything that takes a click is a `Button`, `CheckButton` or `EditBox`.

**The main window on Native.** `Window.create` builds a `Native.window("CraftProfitWindow", L.TITLE, { width = 372, onMoved, onTitleClick })`: sections are children of `frame.content` (the inset), anchored `Native.CONTENT_PAD` (4 px) from every inset edge (on a build without the inset, `content` is the frame and the sections start at the inset's edges, 9 / 6 / 24 px, so the height maths still hold) and stacked 8 px apart (`Window.GAP`, `Layout.stack`). `Window.INNER_WIDTH` = 372 - `INSET_LEFT` 9 - `INSET_RIGHT` 6 - 2 x 4 = 349 px; the three tiles are 111 px each. `Window.contentHeightOf(list)` is the inset height (stacked sections + 2 x `CONTENT_PAD`); the frame height adds `INSET_TOP` 24 and `INSET_BOTTOM` 4, plus 8 px and the pinned host when it shows. Section heights: panel heights from `Layout.panelHeight` (same geometry as `Native.panel`: 2 px edge, 22 px header, 4 px body pad, rows, 2 px edge); a folded Materials panel is `Window.FOLDED_H` = `Native.HEAD_H` + 4 = 26 px (the header keeps its 2 px inside the inset border at the top and the bottom); option rows are `max(CHECK_SIZE, BUTTON_H, INPUT_H) + 2` = 26 px and the Options body is exactly three of them. The banner is `Native.banner(content, 52, Window.INNER_WIDTH)` (the width lets it measure its text before layout): fill and 2 px edge tinted with `Colors.FIXED` by result kind (profit, loss, incomplete, else trivial); its value steps down the game font ladder from `GameFontNormalHuge` (20 px, the largest shadowed `GameFontNormal*`; the old banner started at 22 px) to `GameFontNormal` (12 px) when wider than 120 px. Reagent rows are `Native.listRow` rows with `Colors.text("main")` names and `Colors.text("muted")` values. Drag forwarding (`Native.forwardDrag`): the AH tile, every reagent row and the Materials header move the window like its body, and the click that ends a drag does nothing (no search, no fold). Texts use game font objects (`GameFontDisableSmall` age, `GameFontHighlightSmall` likely line, `GameFontDisable` empty text) painted with `Colors.text("muted")`, a stale age with `Colors.FIXED.stale`; the per-point value is `Colors.FIXED.profit`/`loss` or `Colors.text("main")`. Widgets: `Native.input` for crafts (applied on `OnEditFocusLost`, hooked because the template has its own handler), `Native.check` for track (label capped so it stays in the body) and per-point (label cut before its value; after each render `Window` caps the check with `check:setMaxWidth` to the room left of the value, so the hit area widened over the label never reaches under the value), two `Native.button`s 161 x 22 sharing the third option row: Pin/Unpin and Refresh recipe (see above). The main window is not in `UISpecialFrames` (Escape does not close it). The pinned list inside it and the leveling window are on Native too (see below).

**Known small limits of the main window.** The partial verdict no longer competes with the value: its warning sits on the label line (`banner.warning`) and the main line keeps only the best way to sell. A main line that still does not fit beside the value (a very long item option name in some language) drops to the small font instead of wrapping, and could in theory be cut off next to a very large value.

**The scroll bar maths.** The geometry of the scroll bars is pure and unit tested, in `UI/Layout.lua`: `Layout.scrollThumb(total, visible, offset, trackH)` gives the thumb height and top (never shorter than `SCROLL_MIN_THUMB`, 16 px; `nil` when the list fits), `Layout.scrollOffsetAt(total, visible, trackH, y)` turns a pointer position on the track into a row offset, and `Layout.scrollGrab(total, visible, offset, trackH, y)` gives where on the thumb the pointer holds it: the distance from the thumb top when the pointer is on the thumb, half the thumb height when it is elsewhere on the track (the thumb centres on the pointer), `nil` when the list fits; a drag keeps that grab, so the thumb does not jump when grabbed off-centre. Clicking the track jumps there; dragging the thumb follows the pointer, read each frame with the `GetCursorPosition` global (declared in `.luacheckrc`) and divided by the bar's effective scale. The mouse wheel is handled by the list owners (rows, bar and the empty space of the list).

**The native scroll bar.** `Native.scrollbar(parent, trackH)` returns a bar driven by its owner: `bar.frame`, a plain `Button` `Native.SCROLL_W` = 8 px wide and `trackH` high, hidden at creation; `bar.thumb`; `bar:update(total, visible, offset)` returning whether it shows; `bar.onScroll(offset)`, asked for the offset a click or a drag wants; it uses the pure maths of `UI/Layout.lua` (`Layout.scrollThumb`, `Layout.scrollOffsetAt`, `Layout.scrollGrab`, minimum thumb 16 px). Blizzard's `MinimalScrollBar` template needs a `ScrollBox`, so the bar draws its atlases itself (`Blizzard_SharedXML/Shared/Scroll/MinimalScrollBar.xml`): the track is `minimal-scrollbar-track-top`, `!minimal-scrollbar-track-middle` (the `!` marks a vertically tiling atlas: `SetVertTile(true)`) and `minimal-scrollbar-track-bottom`; the thumb is `minimal-scrollbar-small-thumb-top|middle|bottom` (there is no `minimal-scrollbar-thumb-*`), with the `-over` set while the pointer is over the bar and the `-down` set while dragging, when the client knows them. The caps keep their atlas height (`C_Texture.GetAtlasInfo`; the UI source does not give the sizes), and share the thumb when it is shorter than both. When one piece of the track (or of the thumb) is unknown, that part is a flat texture: track `Colors.text("muted")` at alpha `SCROLL_TRACK_ALPHA` 0.3, thumb `Colors.text("gold")`. The thumb is a plain frame without mouse, so presses land on the track, which knows where the thumb is. ## Price model

- A listing becomes `{ unit, qty }`. A stack row of the scan has its stack price divided by the stack size (`AH.PER_UNIT_REPLICATE = false`, measured).
- `Prices.summarize(listings, n)` sorts by unit price and takes the **median unit price of the n cheapest units** (`n = 5` by default, `settings.medianN`), plus the total volume. Quantities are handled arithmetically, so a listing of one billion units costs the same as one of one unit.
- `Prices.store` and `Prices.merge` write compact rows (a unit above `Util.MAX_COPPER` is refused, and dropped from a save at load) `{ unit, volume, time, full }` into the current market's price table (`CraftProfitDB.markets[key].prices`, see [Saved variables](#saved-variables)); `Prices.get` returns the unit price and its age, and `nil` for the age when the clock cannot be trusted.
- **Volume completeness.** `full` is `true` when the volume counts every unit on offer, and absent otherwise (absent reads as partial everywhere). A search reads at most `AH.MAX_SEARCH_RESULTS` (100) result rows, sorted by price: when the game reports 100 rows or more the list was cut and its volume is only the cheapest part of the market, so `AHAdapter` sets `listings.full = false`; fewer rows, all readable, give `true` (a row skipped as a secret value makes it `false`; a bid-only auction is not on offer and does not). `Controller.recordListings` passes the flag to `Prices.store`. A full scan sums every listing of the replicate list, so `Prices.merge` stores `true`. `DB.initAccount` keeps `row[4]` only when it is `true`. The flag is recorded so a later estimate of sales per day can use complete volumes only; nothing shows it yet.
- `DB.prune` removes prices older than 14 days at load, and prices dated more than a day ahead (`DB.PRICE_FUTURE_SLACK`: written with a clock that ran ahead, their age would stay unknown for good). Less than a day ahead is clock drift: the price is kept, its age unknown.
- Selling uses a commission of 5 % (`settings.cut`, measured). The deposit is ignored: it is refunded when an item sells.

## Leveling list

`Trade.scanKnown` reads every learned recipe of the open profession, grey ones included so the "show grey recipes" option has something to show (`C_TradeSkillUI.GetAllRecipeIDs`, `GetRecipeInfo`, then the usual schematic read), 40 recipes per frame so the client never hitches, and abandons the read if the window closes (a partial list never replaces a good one). `Controller.refreshKnown` runs it on `TRADE_SKILL_LIST_UPDATE`, at most every 5 seconds, and at once on `TRADE_SKILL_SHOW` and `TRADE_SKILL_DATA_SOURCE_CHANGED` (`Controller.onProfessionChanged`: on Forever the profession window has a tab per profession and switching tabs changes the profession without closing the window; the scan in progress is dropped with `Trade.cancelScan` and the 5 s window restarts). Nothing is read while `C_TradeSkillUI.IsDataSourceChanging()` is true (the Blizzard window waits too), and an empty read never replaces a stored list. `Controller.refreshPinDifficulties` runs on the same events. Each finished read is stored with `DB.setKnown` in `CraftProfitCharDB.known = { { key, name, updated, recipes } }` (8 professions, 400 recipes each at most). The profession key is the id of `C_TradeSkillUI.GetBaseProfessionInfo()` when it has one, else the profession name. `Leveling.rank` evaluates each stored recipe with the per point figures forced on, hides the ones with a chance of 0 unless asked, and orders them with `Core.rankByPointCost`. Each recipe is priced with every stored price, from a scan or a search, so no search is needed; the window's age line shows the time of the last full scan (`Prices.snapshotAge`), not the age of the prices used.

A recipe whose cost per point is negative (it pays for itself) ranks first in the cost order, and the more so the rarer the point, because the figure is the money made per point: that order is about money, not speed. The speed order (`Core.rankBySpeed`, setting `levelSort`) puts the highest chance first and breaks ties by cost; the window also shows the crafts per point (`Present.craftsPerPoint`, 1 / chance) so the amount can be read as the loss of one craft times that figure.

## Price history

A recipe is *tracked* with the "Track history" box (account wide, 30 at most, `History.MAX_TRACKED`; unticking pauses recording and keeps the history; the History window's **Delete history** or `/cp history remove <n>` deletes it, see below). After every full scan and every price search, `History.record` writes one point per item of each active tracked recipe **touched by that update**, provided every required item has a price (the output of a bind-on-pickup recipe is never required). A point is `{ t, unit, volume, low, high, n, full }` with `t` the time of the operation, so the items of one recipe share a timestamp and the recipe's cost and net can be rebuilt for that date; `full` is copied from the price row (`row[4]`): `true` for a complete volume, absent otherwise. A merged daily point is `full` only if every point merged into it was (and keeps the sum of their counts). Points saved before the flag have none and read as partial; `History.sanitize` turns any value but `true` into absent, so compaction stays idempotent. `History.volumeSeries(series, now, days)` → `{ day, volume, full }` per local day: the volume of the day's last complete point (the quantity on offer at the end of the day; for a merged day, its average volume), nil when no point of the day is complete, and `full` when all of them were. Sales per day are not derived yet.

Retention (`History.compact`): all points for 7 days (`History.RAW_SECONDS`), then one point per day up to 60 days (`DAILY_SECONDS`); there is no weekly tier. A merged point keeps the weighted average, the low, the high and the number of measurements, and is dated at the start of its local calendar day (computed from the date fields, so a daylight saving change day is one day; a save made before this rule has merged points dated at UTC midnight, which show on the local day containing that instant: a one-time shift of at most a day, corrected by the next compaction). A day is kept while any part of it is within 60 days (`dayStart + DAY > now - DAILY_SECONDS`): the rule depends only on the day's start, never on the date of a point in it, so a point 59.9 days old is never lost because its day began more than 60 days ago, and compacting again changes nothing (the cost: a point up to one day past 60 days survives when it shares a day with a newer one). Each tier has its own cap, keeping its newest points: raw `History.MAX_RAW` = 150, daily `MAX_DAILY` = 62, so at most 212 points per item. The daily span holds 55 buckets at most, so its cap never binds on sane data; a busy week only drops its oldest raw points and never the daily history. Saves from the earlier retention (raw 14 days, daily 90, weekly a year) compact at load (`History.sanitize`): raw points 7 to 14 days old become daily points, daily points of the last 60 days stay as they are, older daily points and every weekly point are dropped. A point dated more than a day ahead (`History.FUTURE_SLACK`) is dropped when a new point is added to its series, so a clock that ran ahead cannot block recording; loading and compacting keep it (a clock set back for a while never erases newer history), and `History.compact` with an invalid `now` returns the series unchanged; `History.record` counts a recipe only when at least one point was really added. Size: the game writes saved variables one element per line, indented, with `-- [n]` comments, so a point takes about 150 to 180 bytes in the saved file and a full series (212 points) about 35 KB per item, against about 120 KB for the earlier worst case (725 points). The `full` flag adds about 20 bytes to a complete point (absent costs nothing), about 5 KB per item at the cap. The caps are rarely reached: 150 raw points need 150 measurements in 7 days. With 30 tracked recipes (60 to 90 items) the worst case is 2 to 3 MB; if that proves too much, lower `History.MAX_RAW`. A tracked recipe has its reagents, crafted item and disenchant materials, typically 3 to 6 items, shared between recipes that use them. **Refresh pinned** prices only the pinned recipes and **Refresh recipe** only the recipe on screen; tracked recipes are fed by scans and by any search that touches their items. The History window shows it (below).

Pure computations for the history view (no UI yet), all tested with hand-made series and a stubbed local date:

- **Local days.** `History.dayOf(t)` (start of the local calendar day) and `History.weekday(t)` (1 Monday to 7 Sunday) read the local date through `History.setDateFn(dateFn, timeFn)`: `dateFn` like `date("*t", t)`, `timeFn` like `time(fields)`; without them they use the game's `date` and `time`. The day start is `timeFn` of the date fields at 00:00, so a daylight saving day (23 or 25 hours) is one day with one weekday; it is accepted only if it equals the clock-field estimate (t minus the local hour, minute and second) or differs from it by one hour, else the estimate is used (a time function that ignores its argument, as the fake game clock does). A date function that fails or returns unusable fields gives nil: the point is skipped by the daily views and left unmerged by compaction, nothing raises. Tests inject a stub clock (`tests/stubclock.lua`: fixed offset, optional one-hour daylight saving period), so nothing depends on the machine's time zone; also checked with the real `os.date`/`os.time` under `TZ=Europe/Paris` and `America/Los_Angeles` on their 2026 change days.
- **`History.dailySeries(series, now, days)`** → `{ day, avg, low, high, n }` ascending, one entry per local day of the last `days` days that has data (days without data are absent). Every point goes to the local day holding its date (merged points are dated at their local day start), average weighted by count. Points after `now` and hostile points are ignored; the saved series is never mutated.
- **`History.usual(series, now)`** → `{ price, days, measures }`: median of the daily averages of the last 30 days (`USUAL_DAYS`), nil under 3 distinct days (`USUAL_MIN_DAYS`).
- **`History.compare(today, usual)`** → `{ pct, tone }`: rounded percent difference, tone `flat` within ±3 % (`FLAT_PERCENT`), else `up` or `down`; nil when either value is not finite or the usual price is 0 or less (never a division by 0).
- **`History.weekdayProfile(days, usual)`** → 7 entries Monday to Sunday `{ pct, n }`: the mean of that weekday's daily values against the usual price; `pct` is nil under 2 days (`WEEKDAY_MIN_DAYS`) or without a usable usual price.
- **`HistoryView.recipeDays(recipe, itemSeriesOf, now, days, cut, itemsOf)`** → per measured day `{ day, materials, sale, net, carried, materialsCarried, saleCarried, n }`. `itemsOf` is the function recording uses (`Controller.historyItems`); a crafted item it does not require (bound on pickup) is never sold, so `sale` and `net` stay nil and the materials remain. An item without a point on a day takes its last known daily price (from the whole daily tier, even before the period) and the day is marked `carried` (any price carried); `materialsCarried` is false, `"some"` or `"all"` (all reagent prices carried) and `saleCarried` false or `"all"`, each set when its value is known; before an item's first point there is no price and whatever needs it stays nil. Materials and sale use `Core.sumCost` and `Core.netSale`, the functions `Evaluate` uses (a test checks the net against `Evaluate.run` for the same prices). The net is the auction house sale (after commission) minus the materials: it is not `Evaluate`'s net, which takes the best of the AH, vendor and disenchant options; vendor and disenchant are not covered.
- **`HistoryView.summary(days, field)`** → `{ today, usual, low, high, measures, daysCovered, enough, todayDay, lowDay, highDay }` (the days of today, of the lowest and of the highest value; the newest on a tie) for one view: `field` is `net`, `materials` or `sale` for `recipeDays` entries; without it the entries are an item's `dailySeries`. A day whose `<field>Carried` is `"all"` only repeats older prices and is skipped (so a day where only the crafted item was measured never becomes the materials' "today"). **"today" is the newest day with a measurement**, not the calendar day, and the usual price is the median of the 30 days up to that day; `enough` is false (and `usual` nil) under 3 days.
- **`HistoryView.compare(summary, higherIsGood)`** → `History.compare(today, usual)` with `good` (true for good news, false for bad, nil flat), nil unless `summary.enough`.
- **`HistoryView.profitCompare(summary)`** → `{ gap, tone, good }` or nil: the `net` summary's today against its usual profit in money, for any sign of either (`History.compare` refuses a usual of 0 or less). `gap = today - usual`; `flat` when `|gap|` is within `FLAT_PERCENT` % of `|usual|` (a usual of exactly 0: only a gap of 0), else `up` (good) or `down` (bad); nil unless `summary.enough` and both are finite.
- **`HistoryView.indicators(recipe, itemSeriesOf, now, itemsOf, cut)`** → `{ materials, sale, netToday }`, the first two `{ pct, tone, good }` or nil: materials cheaper and a sale higher than usual are good, the opposite bad, `good` is nil within the flat band. `netToday` is the auction house profit of the newest day (`summary(days, "net").today`), nil without a sale.

**Freshness rule (24 h).** Because "today" is the newest measured day, a comparison is shown as current only when the newest measurement of any of the recipe's items is at most 24 hours old (`Controller.HISTORY_FRESH`). Otherwise `historyList` gives `fresh = false` and no `indicator`, and the arrows are hidden. The main window arrows (step 4) follow the same rule.

**Pausing and deleting.**
- Pausing (`Controller.setHistoryActive(recipeID, false)`, the History window's **Pause tracking**, or unticking *Track history*) stops recording and keeps every point. A paused recipe still counts toward the limit of 30 and still protects its items from pruning; resuming (`History.track`) records again.
- Deleting (`Controller.deleteHistory(recipeID)`, or `/cp history remove <n>` through the same code) removes the recipe from the tracked list, then deletes series in **every market** of `CraftProfitDB.markets` (other rulesets and factions too), conservatively:
  - Only an id from the removed recipe's own list can go, and only when no remaining tracked recipe (active or paused) could need it.
  - Both lists come from `Controller.historyItemsAll(recipe)`: reagents, crafted item and every disenchant material the crafted item can give, as if the character knew Enchanting. It does not depend on the current character the way `historyItems` does.
  - While a remaining recipe's crafted item is not loaded yet (its disenchant materials are unknown), only the removed recipe's own reagents and crafted item can go, never a disenchant material.
  - Series that were never in the removed recipe's list are left alone.
  - Current prices (`market.prices`) are never touched. `History.prune` (drop everything no tracked recipe needs, current market) is no longer called by the delete paths. The window prints "History of %s deleted"; the command keeps its own message.

**History window data** (`Boot.lua`):
- `Controller.historyList()` → `{ recipe, active, indicator, fresh, atLoss }` per tracked recipe, in saved order. `indicator` is `HistoryView.indicators` (with `good`), present only when there is enough data and the data is fresh. `atLoss` (fresh data only, else nil; nil without a sale) is `netToday <= 0`: crafting and selling at the auction house loses money or earns nothing on the newest day.
- `Controller.historyData(recipeID, view, period)` → `{ recipe, items, view, period, chart, summary, weekday, status, paused, measures, days, market, goal, compare, profit, commission }`, or nil for a recipe that is not tracked.
  - `profit` is the recipe's auction house profit whatever the view (item views included): `{ today, todayDay, usual, enough, compare, atLoss }`, `today` from `HistoryView.summary(rows, "net")` over the period's recipe rows, `usual` and `enough` over 30 days like every view, `compare = HistoryView.profitCompare(profit)`, `atLoss` true when `today` is a number of 0 or less. Vendor and disenchant values are not counted.
  - `view` is `net`, `materials`, `sale` or `item:<id>` (default `net`); `period` is 7, 30 or 60 (default 30).
  - A recipe view charts `HistoryView.recipeDays`; an item view charts `History.dailySeries`.
  - The usual price and `enough` always cover 30 days, whatever the period; the other key figures cover the period.
  - `chart` is the model for `Chart:set`, ending today (`newest = History.dayOf(now)`).
  - `weekday` is `History.weekdayProfile` of the period's days, skipping days made only of carried prices.
  - `status` is `nodata` (fewer than 3 days; `measures` and `days` over 30 days are given for the message), else `paused`, else `ok`.
  - `items` holds one entry per item: `{ key = "item:<id>", itemID, name, icon, group }`, `group` being `materials` (a reagent), `crafted` (the crafted item, when it is sold) or `disenchant`. The recipe views (net, materials, sale) are the window's tabs, not items.
  - `goal` says what the shown price matters for: `buy` (materials, or a reagent), `sell` (sale, the crafted item, a disenchant material) or `craft` (net). `compare` is `HistoryView.compare(summary, goal ~= "buy")`: a lower price is good news when buying, a higher one otherwise; nil without enough data. In the Profit view it is `profit.compare` instead (money, any sign of the usual). `commission` is the auction house cut in percent (`settings.cut` × 100, two decimals), for the Profit caption.
  - `market` is `Controller.marketName()`: ruleset name, localized faction, `(HC)` for hardcore.
- `Controller.historyItemsOf(recipe)` → the item ids for the icon row: reagents, then the crafted item unless bound on pickup, then disenchant materials, from `Controller.historyItems`.
- `Controller.itemIcon(itemID)` tries `C_Item.GetItemIconByID`, then the texture field of `GetItemInfo`, secret-safe. It is not measured on Forever: `historyData` calls it in `pcall`, and the window falls back to the question mark icon.
- `Controller.openHistory(recipeID)` shows the window and selects the recipe.

The mouse wheel and the scroll bar (`parts.bar.onScroll`) only call `repaintList()`: rows and bar from the cache, no data call, no repaint of the right side (tested with counters on `historyList` and `historyData`).
- **Right column**, top to bottom:
  - **Verdict panel**, titled with the recipe name, three 16 px lines (`HistoryWindow.verdictLines(data)` lists the non-empty ones in order; they fill `parts.lines[1..3]` from the top). `profitLine`: `data.profit` as `HISTORY_AH_TODAY` / `HISTORY_AH_ON` with `HISTORY_PROFIT_AMOUNT` (green), `HISTORY_LOSS` (red) or `HISTORY_BREAK_EVEN` (grey), empty when the profit is unknown. `verdictLine`: `"<What> today: <amount>"` (`HISTORY_VERDICT_TODAY`; `HISTORY_VERDICT_ON` with the date when the newest measured day is not today), `<What>` being the tab's name or the item's; empty in the Profit view. `compareLine`: `data.compare` as a sentence, "12 % cheaper than usual (3s55): good time to buy" (`HISTORY_CHEAPER` for a price to buy, `HISTORY_LOWER` otherwise, `HISTORY_HIGHER`, `HISTORY_ABOUT` within ±3 %), the advice (`HISTORY_GOOD_BUY` / `SELL` / `CRAFT` by `goal`) only on good news; green good, red bad, grey flat. When `profit.atLoss`, good news is grey without advice. In the Profit view the sentence is in money: `HISTORY_PROFIT_BETTER` (green with `HISTORY_GOOD_CRAFT` while at a profit), `HISTORY_PROFIT_LESS_LOSS` (grey, better but still at a loss), `HISTORY_PROFIT_WORSE` (red), `HISTORY_ABOUT`. No line without enough data.
  - **Chart panel.** Three tabs, *Materials cost*, *Sale price*, *Profit* (views `materials`, `sale`, `net`; widths from the label at 7 px a letter), lit with a gold line on the active one and none lit when an item is shown; the 7 / 30 / 60 days buttons at the right of the same row. Under them the item icons (24 px) in groups, each with a tiny muted caption (*Materials*, *Crafted item*, *Disenchant*) and a 1 px muted separator between two groups on a line; only the groups that exist show. `HistoryWindow.layoutIcons(groups, width)` (pure, tested) flows the groups on lines: a group that does not fit the rest of a line starts the next one, a group wider than a line wraps its icons; two lines at most. Then a caption saying what is drawn (`HISTORY_CAPTION_NET` with the real commission, `_MATERIALS`, `_SALE`, `_ITEM`) and the chart (`Chart.new(area, w, 170, window)`, so drags on it move the window), with `chart.dateText = HistoryWindow.dateText` and `chart.bubbleText = HistoryWindow.bubbleLines`.
  - **Key figures panel.** Four cells: *Now*, *Usual* (note "30-day median"), and the lowest and highest day of the period (*Worst day* / *Best day* for Profit, *Cheapest day* / *Priciest day* for Materials cost, *Lowest* / *Highest* otherwise), each amount with its date under it, muted; then "N measurements over D days".
  - **Typical week panel.** `Chart.newWeekday` with the weekday names; "Shows after about two weeks of data." on one muted line while no weekday has 2 days.
  - **Actions.** The paused status line, then **Pause tracking** / **Resume tracking** and **Delete history**. The first click on Delete arms it: its label becomes "Click again to delete" for `CONFIRM_SECONDS` = 4 (`C_Timer.After`). A second click within that time deletes. Choosing another recipe, closing the window or the timeout disarms it. There is no game dialog.
- **Wording of amounts.** A Profit amount below zero reads "loss 9s40c" (`HISTORY_LOSS`), never with a minus sign: in the verdict, the figures and the bubble. The chart's axis keeps plain signed amounts (`-3g 10s`) below its zero line.
- **Hover bubble** (`HistoryWindow.bubbleLines(row)`): the date, the value (`HISTORY_LABEL_VALUE`), for Profit the day's sale value and materials cost, for an item the average and low - high, the number of measurements, and the *carried* note.
- **Empty states.** No tracked recipe (`HISTORY_NONE`) or nothing selected (`HISTORY_SELECT`): the message alone on the right. Not enough data: the verdict and chart panels stay (tabs, icons, caption) with `HISTORY_NODATA` in place of the chart; the figures and week panels hide.
- **Selection and drags.** Selecting a recipe resets the view to Profit and keeps the period. A refresh keeps selection, view and period, and drops a selection that is no longer tracked. Buttons and rows forward drags to the window; a click that ends a drag runs nothing.

**Entry points.** The **History** button under the pinned list (right of Leveling), the **History** button in the options window's Windows panel (now 2 × 2), and `/cp history`:
- `/cp history` opens the window;
- `/cp history <n>` opens it on the n-th tracked recipe, or prints `HISTORY_NO_SUCH`;
- `/cp history list` prints the tracked recipes in chat (the old behaviour);
- `/cp history remove <n>` deletes one, as above.

**Chart geometry** (`ChartModel.lua`, pure, all amounts in copper, y measured from the top of the area):
- `scale(lo, hi, steps)` → `{ min, max, step, ticks }`. Padding is 5 %; a range of 0 is padded by 10 % of the value, at least 1 copper. The scale never goes below 0 when `lo >= 0`. Steps are 1, 2 or 5 × 10^k (at least 1) for about `steps` intervals (default 4, kept within 2 to 20), and min and max are multiples of the step, so 0 is a tick whenever the range crosses it (a loss). Always `max > min`. A bound that is not finite is ignored, and the padded range stays within ±`Util.MAX_COPPER`, so a hostile value never produces a long tick list.
- `priceLabel(copper)` → plain text, never icons: `12g 40s`, `12g`, `40s 5c`, `5c`, `-3g 10s`. From 1000 gold it shows thousands of gold rounded down to one decimal (`1.2k g`, `1k g`), with no decimal from 100k (`999k g`). From a million gold it shows millions the same way (`1M g`, `12.3M g`). Amounts are capped at `Util.MAX_COPPER`, which shows as `1000M g`. Anything not finite gives `?`.
- `slots(period)` → `{ count, index(day, newest) }` for 1 to 62 days ending at `newest`. Days are counted by rounding, so a 23 or 25 hour day counts once.
- `range(days, period, newest, field)` → `{ first, last, count }`: the slots the chart draws, ending at `newest` (default the newest drawn day) and starting at the oldest drawn day inside the period, at least `MIN_SLOTS` = 7 and at most `period` slots. Four days of data on a 60-day period draw over 7 slots, not 60.
- `dateTicks(count, newest)` → the first, middle and last slot `{ slot, t }`, `t` at midday of the slot's day (safe from 23 or 25 hour days).
- `zeroY(scale, height)` → the y of 0, nil when the scale does not hold it.
- `dashes(width, dash, gap)` → the `{ x, w }` segments of a dashed line, the last one cut at the width, at most `MAX_DASHES`.
- `extent(days, field)` → the lowest and highest values a chart of those rows would draw.
- `bars(days, scale, width, height, field, period, newest)` → `{ slot, x, w, yLow, yHigh, yAvg, yEdge, carried, row }`. The rows are either `HistoryView.recipeDays` charted on `field` (`net`, `materials`, `sale`: low = high = the value, carried from `<field>Carried`, else `carried`) or `History.dailySeries` rows when `field` is nil (avg, low, high).
  - A net bar stands on the zero line: from 0 to the value, up for a profit, down for a loss.
  - `yEdge` is the bar's outer end: the value for a recipe view, the high for an item.
  - A bar covers 60 % of its slot; `newest` defaults to the newest drawn day.
  - A row without a finite value keeps its slot empty: a gap, never a zero. Values off the scale are clamped.
- `usualY(usual, scale, height)` → `{ y, outside }`; `outside` is `above` or `below` when the usual price is off the scale, and the line then sits on that border.
- `weekdayBars(profile, width, height)` → 7 entries, Monday first, `{ x, w, y, h, pct, n, empty }`, around a zero line at mid-height, plus `limit`. The scale is symmetric (±limit %): the largest |pct| rounded up to a multiple of 5, at least 10. A weekday under 2 days is empty.

Gridline and zero line colours are in `Colors.CHART`; the usual line uses the game's gold text colour.

**Chart widget** (`UI/Chart.lua`) draws that geometry with coloured textures on plain frames; the plot sits on its own `InsetFrameTemplate` with a darker backdrop.
- **Creation.** `Chart.new(parent, width, height, window)` returns an object; its `frame` starts shown and the caller anchors it. The area is a 60 px left gutter for the amounts, the plot, and a 14 px row of dates under it. A size that is not finite or not positive falls back to 400 × 240. With `window` (a `Native.window`), each slot button forwards a left drag to it through `Native.forwardDrag`, so a drag on the plot moves the window as a drag on its body does; no hover is reported while it moves, and a drag start ends the current hover. Without `window`, the slot buttons only hover.
- **`chart:set(model)`.** The model is `{ days, field, scale, usual, usualLabel, period, newest, carriedTint }`; `period` defaults to 30, and nil or anything unusable clears the chart.
  - The x range is `ChartModel.range`; its slot count drives the bar width.
  - The scale comes from the days and the usual price when the model gives none; the net view always holds 0, with a 2 px zero line and the axis amount `0`.
  - Each day: a semi-transparent body (`BODY_ALPHA`, low to high, or zero to the value for net), a lighter 2 px outer edge, a bright dash and a 4 px dot at the value. Green or red by the net's sign, gold for other views. A carried day multiplies its alpha by `carriedTint` (default 0.4).
  - Faint 1 px gridlines with their `priceLabel` in `GameFontHighlightSmall`; dates of the first, middle and last slot under the plot from `chart.dateText(t)`.
  - The usual price is a gold dashed line (6 px dashes, 4 px gaps) with a chip at the right end: `usualLabel` and the amount, with ` ^` or ` v` when it is clamped off the scale.
  - Everything stays inside the plot, every bar keeps at least one pixel visible; ticks that are not finite numbers are skipped, and a `field` that is not a string draws nothing.
- **Hover.** One invisible Button per slot. On enter, the column is highlighted and, for a day with data, the chart draws a bubble (a dark panel with a thin gold rim, `BUBBLE_W` = 260 px, normal-size font, up to 7 lines) from `chart.bubbleText(row)`, inside the plot, right of the column or left of it near the right edge. `chart.onHover(row, slot)` (optional) is called too, with nil on leave. The window words the bubble; the chart only draws it.
- **`chart:clear()`** empties the chart. When a day was hovered it also calls `onHover(nil)` and hides the bubble, because a hidden button fires no `OnLeave` (`set` clears first, so a redraw ends the hover too).
- **Typical week.** `Chart.newWeekday(parent, width, height, names)` → `week` with `week:set(profile, emptyText)`: the percentage above each bar (rounded, within ±999: `-20%`, `0%`, `+13%`), the bar around a zero line (green above, red below, none under 2 days) and the weekday name under it. When no weekday has a value, only `emptyText` shows, on one muted line.
- **Pools.** Bars (body, edge, dash, dot), gridlines and labels, dashes, dates, slot buttons and line segments come from pools. A redraw reuses what exists and hides the rest, so 60 days then 7 then 60 creates nothing new. Nothing runs per frame: drawing happens only in `set`, a hover and `week:set`.
- **Lines.** `Chart.USE_LINES` (true) adds a 2 px line through the daily values, one `CreateLine` segment between neighbouring slots: the line stops at a gap and a lone day draws no segment. When `CreateLine` is missing, returns nothing or raises, `chart.linesOk` is false and only the bars stay. It is on because the probe showed `CreateLine` works on Forever (`/cppn line`, [probe-findings.md](probe-findings.md) F14).

## Evaluation

`Evaluate.run(ctx)` returns `{ recipe, crafts, cost, options, best, bestValue, net, incomplete, perPoint, oldestAge }`.

- **Cost** = sum of quantity × unit price of the reagents (`Core.sumCost`); `nil` when any price is missing.
- **Options**: `ah` (net sale, `n/a` for bind-on-pickup), `vendor` (sell price × quantity), `disenchant` (expected value net of the commission, plus `likely`: the most probable outcome). Each has a status `ok`, `unknown`, `na` or, for the disenchant, `nodata`.
- **Disenchant rules**: armor or weapon of quality 2 to 4 only; a bind-on-pickup item only when the character knows Enchanting (`Trade.hasProfession(333)`: the skill line id, language independent); an item level with no row in the table gives `nodata` (an unknown item level stays `unknown`). `nodata` is shown as "no data" on the disenchant line and tile; `Core.bestOption` does not count it as incomplete, since no search can fill it, so the window never says *PRICES MISSING* for it; when no other option can sell the item, the verdict is `VERDICT_NO_DATA` ("No disenchant data for this item").
- **Best** = the `ok` option with the highest value (`Core.bestOption`); **net** = best value − cost.
- **Per point** (when enabled) = `(cost − bestValue) / chance`, with the chance from `Data/Skillup` by recipe colour. Computed before the multiplier is applied, so it is always per point.
- **Crafts** (1 to 9999, `Evaluate.craftCount`): after computing for one craft, quantities, cost, option values, best value and net are multiplied; per point and `likely` are not.

## Measured behaviour of the beta

Measured in game on build 1.60.1, French client (details in [probe-findings.md](probe-findings.md)):

- Reagents are commodities: `COMMODITY_SEARCH_RESULTS_UPDATED` with the item id, fields `unitPrice` and `quantity`. Gear uses `ITEM_SEARCH_RESULTS_UPDATED` with an item key table, fields `buyoutAmount` and `quantity`. The first result event already holds the rows; about half the searches get a second identical event 0.1 to 0.4 s later, ignored. A search with no result still fires its event (see F13).
- A full scan returns about 79,000 rows of 17 values; `buyout` is the price of the **whole stack**. `REPLICATE_ITEM_LIST_UPDATE` fires hundreds of times per scan. A scan inside the 15 minute window is ignored silently, no event.
- The AH commission is 5 % of the sale price, the deposit is refunded on sale.
- `GetProfessionInfo` returns the skill line id as its 7th value (164 for Blacksmithing, 129 for First Aid); `GetNumSkillLines` does not exist.
- The Mainline auction house frames exist with their usual members. Setting the quantity input alone leaves the quote on one unit; its `OnTextChanged` handler must run with `userInput = true`.

## Constraints that shape the code

- **Secret values.** Some game values are secret: comparing, concatenating, indexing a table with them or doing arithmetic on them raises. Every value read from the game is checked with `Util.isSecret` before use and a secret field is dropped (nil): `Controller.itemInfo` (called under `pcall`) and the recipe read do this field by field, and a recipe's difficulty is stored as a known name (`optimal`, `medium`, `easy`, `trivial`) or nil, since it is used as a table key. Item names are read inside `pcall`.
- **Division by zero raises.** The client rejects a literal zero divisor (`0 / 0`, `1 / 0`). Every divisor is guarded, NaN and infinity are built from `math.huge`, and a test refuses a literal zero divisor anywhere in the addon.
- **Lua 5.1 only**, no `table.unpack`, `//`, goto or integer division; the offline tests run on LuaJIT, so `/cp selftest` re-checks a few behaviours inside the game's own Lua.
- **The full scan is limited** to one per 15 minutes per account, shared with every addon.
- **No API for sales history**: CraftProfit does not know how fast an item sells.

## Localization

`Locale.select(GetLocale())` picks the table; a missing key falls back to enUS, then to the key itself. `esMX` is an alias of `esES`. User-facing words live in the locales; a few formats are still built in code (the likely-disenchant line `"%s%%: %sx %s = %s"` in `Present`, the `x` of quantities, `#id` for an unnamed item). Tests check that frFR and esES define exactly the enUS keys, keep its format specifiers (`%d`, `%s`) in the same order and are never empty. See [CONTRIBUTING.md](../CONTRIBUTING.md#adding-or-fixing-a-language).

## Probe addon
